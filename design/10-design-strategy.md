## 2. Design Principles

- **เริ่มจากงานหลักของผู้ใช้:** ให้สมาชิกตรวจงานและอัปเดตสถานะได้ตรงไปตรงมา ส่วนการสร้าง/มอบหมายงานและการดูภาพรวมต้องสอดคล้องกับบทบาท
- **สม่ำเสมอและคาดเดาได้:** ใช้ชื่อสถานะ ป้ายกำกับ รูปแบบวันที่ และข้อความยืนยัน/ผิดพลาดแบบเดียวกัน
- **Privacy by design:** จำกัดข้อมูลตามกลุ่มและบทบาทตั้งแต่จุดเข้าถึงข้อมูล ไม่พึ่งการซ่อนปุ่มบนหน้าจอเพียงอย่างเดียว
- **ตรวจสอบย้อนหลังได้:** เก็บหลักฐานและประวัติการเปลี่ยนเจ้าของงานพร้อมเวลา โดยไม่เปิดทางให้สมาชิกทั่วไปแก้หรือลบประวัติ
- **สื่อสารอย่างเป็นกลาง:** ใช้ถ้อยคำที่บอกเหตุการณ์และการเปลี่ยนแปลง ไม่กล่าวโทษหรือจัดอันดับบุคคลในประวัติงาน
- **เข้าถึงได้และยืดหยุ่นต่ออุปกรณ์:** ออกแบบข้อความและการควบคุมให้เข้าใจได้ ไม่ใช้สีเป็นสัญญาณเพียงอย่างเดียว และคำนึงถึงการใช้งานบนหน้าจอขนาดเล็ก ทั้งนี้ mobile responsive ยังเป็นประเด็น OI-03 ที่ต้องยืนยันก่อนกำหนดเป็น baseline
- **รักษาขอบเขต MVP:** ระบบติดตามงานและหลักฐาน ไม่สร้างระบบแชต/วิดีโอคอลหรือเชื่อมระบบให้คะแนนมหาวิทยาลัย (DEC-01, SRS C-02)

## 3. Candidate Strategies / Alternatives

ตารางนี้บันทึกทางเลือกและแนวทางที่เสนอให้ใช้ในแบบออกแบบ โดยอิง requirement/decision ที่มีอยู่ หากทางเลือกยังขึ้นกับ OI ใน SRS ให้ถือว่ายังไม่ใช่ข้อยุติใหม่

| Decision Area | Option A | Option B | Selected Option / Direction | Rationale | Trade-off / Status |
|---|---|---|---|---|---|
| การสื่อสารในระบบ | สร้างแชต/วิดีโอคอลในตัว | ใช้ช่องทางภายนอกที่ทีมมีอยู่ และให้ระบบโฟกัสติดตามงาน | Option B — ยืนยันตาม DEC-01 | ลดขอบเขตและให้ระบบมุ่งจัดการงานกับหลักฐาน | ผู้ใช้ต้องสลับไปช่องทางอื่นเพื่อสนทนา |
| สิทธิ์อาจารย์ | เห็นและแก้ไขงานทุกสถานะ | ดู Dashboard และหลักฐานที่อนุญาตแบบอ่านอย่างเดียว | Option B — ยืนยันตาม DEC-02 และ BR-03 | ปกป้องพื้นที่ทำงานระหว่างดำเนินงานและจำกัดการเข้าถึง | อาจารย์ไม่เห็นรายละเอียด WIP; รายละเอียดการมองเห็นให้ยึด SRS |
| การจัดการหลักฐานก่อนปิดงาน | อนุญาตให้ Done โดยไม่ต้องแนบหลักฐาน | บังคับแนบหลักฐานอย่างน้อยหนึ่งรูปแบบ | Option B | ตรงกับ FR-04 และ BR-01 ช่วยให้ตรวจสอบงานที่ส่งแล้วได้ | เพิ่มขั้นตอนก่อนปิดงาน และต้องแจ้งวิธีแก้เมื่อหลักฐานไม่ครบ |
| ประวัติการมอบหมายงาน | เก็บเฉพาะผู้รับผิดชอบปัจจุบัน | เก็บผู้รับผิดชอบเดิม/ใหม่และเวลาเป็นประวัติ | Option B | รองรับ FR-05, BR-04 และ NFR-03 | ต้องจัดเก็บประวัติโดยไม่เปิดให้แก้/ลบย้อนหลัง และคำนึงถึงความเป็นส่วนตัว |
| การจัดเก็บหลักฐาน | อัปโหลดไฟล์ทั้งหมดเข้าแอป | รองรับไฟล์ ลิงก์ภายนอก และข้อความ | Option B — ตาม SRS/DR-02 | รองรับงานหลายชนิดและลดการบังคับให้ย้ายไฟล์จากบริการเดิม | ลิงก์ภายนอกอาจหมดอายุหรือสิทธิ์ไม่ถูกต้อง; วิธีตรวจ URL/ขนาดไฟล์ยังต้องกำหนดใน detailed design |
| ขอบเขตข้อมูล | เก็บข้อมูลรวมโดยไม่แยกกลุ่ม | จำกัดการเข้าถึงตามรายวิชา/กลุ่มและบทบาท | Option B | ตรงกับ NFR-02, FR-11 และ BR-03 | เพิ่มความซับซ้อนของการตรวจสิทธิ์และการทดสอบข้ามกลุ่ม |
| เงื่อนไขเปิด peer evaluation | ล็อกให้ประเมินได้เมื่องาน Done เท่านั้น | กำหนดช่วงเวลาหรือเงื่อนไขอื่นที่ทีม/อาจารย์ตกลง | ยังไม่เลือก — คง OI-01 เป็น TBD | SRS ระบุว่ายังต้องยืนยันเงื่อนไขและไม่ควรสมมติ transition | แบบจำลองและสิทธิ์การเข้าถึงยังต้องปรับหลังได้คำตอบ |
| การแจ้งเตือนกำหนดส่ง | รวมไว้ใน MVP | เลื่อนไปก่อนจนกว่าจะยืนยันความคุ้มค่า | ยังไม่เลือก — คง OI-02 เป็น TBD; FR-10 Deferred | FR-10 เป็น Could และ Needs Follow-up | ไม่ควรสร้าง dependency หรือออกแบบช่องทางแจ้งเตือนถาวรก่อนล็อก scope |

| Responsive access (pending confirmation) | จัดลำดับเนื้อหาและพื้นที่กดให้รองรับจอเล็ก พร้อมทดสอบบนอุปกรณ์จริง | OI-03; VF-05 อ้าง NFR-05 แต่ SRS ส่วนรายการ NFR มีเพียง NFR-01–04 | ยังไม่นับเป็น baseline; ตรวจและแก้ความไม่สอดคล้องของ NFR-05/OI-03 ก่อนกำหนดเกณฑ์รับมอบ |

## 5. Architecture / UX Constraints

- ระบบเป็น stand-alone สำหรับหนึ่งรายวิชา/โครงการ และไม่เชื่อมต่อระบบให้คะแนนมหาวิทยาลัยหรือ API ของแชต (SRS C-02, EXT-02/03)
- ผู้ใช้ต้องเข้าสู่ระบบผ่านอินเทอร์เน็ต; SRS ระบุสภาพแวดล้อมเป็น web-based แต่ยังไม่กำหนดเทคโนโลยี framework, hosting หรือฐานข้อมูล จึงไม่เลือกเทคโนโลยีในเอกสารกลยุทธ์นี้
- ข้อมูลและหลักฐานต้องแยกตามกลุ่ม/รายวิชา และสิทธิ์ต้องถูกบังคับใช้กับทั้งข้อมูลหลักและไฟล์/ลิงก์ที่เกี่ยวข้อง (NFR-02, BR-03)
- สมาชิกแก้สถานะได้เฉพาะงานที่ตนรับผิดชอบ ยกเว้นการเปลี่ยนผู้รับผิดชอบโดยหัวหน้ากลุ่มตาม BR-02; อาจารย์เป็น read-only
- การเปลี่ยนเป็น Done ต้องมีหลักฐานอย่างน้อยหนึ่งรูปแบบ: ไฟล์ ลิงก์ หรือข้อความ (BR-01)
- ประวัติเปลี่ยนเจ้าของงานต้องเก็บชื่อผู้รับผิดชอบเดิม/ใหม่และเวลา และไม่เปิดให้สมาชิกแก้หรือลบย้อนหลัง (BR-04, NFR-03)
- ใช้ถ้อยคำเป็นกลางใน History Log (NFR-04); หลีกเลี่ยงการเปิดเผยข้อมูล WIP แก่อาจารย์ตามขอบเขตที่บันทึกใน DEC-02/SRS
- Peer Evaluation ต้องรองรับเกณฑ์ที่ทีมตกลง แต่เวลาหรือเงื่อนไขการเปิดรอบยังเป็น OI-01; ไม่กำหนดสถานะใหม่หรือ policy ที่ SRS ยังไม่ยืนยัน
- FR-10 (แจ้งเตือน) และ FR-12 (บันทึกข้อตกลง) เป็น Deferred/Needs Follow-up; ออกแบบเป็นส่วนขยายได้ แต่ยังไม่นับเป็นขอบเขตที่ยืนยันแล้ว
- SRS มี OI-03 เรื่อง mobile responsive และ VF-05 อ้าง NFR-05 แต่ตาราง NFR ใน SRS มีเพียง NFR-01–04; ต้องกระทบยอดรหัส/สถานะนี้ก่อนใช้เป็นเกณฑ์รับมอบ
