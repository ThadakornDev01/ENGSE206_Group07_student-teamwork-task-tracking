# 05 — Requirement Backlog and Prioritization

> **Week 5 deliverable** > Requirement ต้องระบุได้ ตรวจสอบได้ และเชื่อมโยงกับ stakeholder/value ที่ชัดเจน
> เวอร์ชัน: v0.1 | สถานะ: Baseline Draft (Merged & Reviewed)

## 1. Prioritization Method

เลือกใช้วิธีหนึ่ง เช่น MoSCoW, Value vs Effort, Kano หรือวิธีที่อาจารย์กำหนด

- **วิธีที่ใช้:** MoSCoW (Must / Should / Could / Won't yet)
- **หลักเกณฑ์:** พิจารณาจัดลำดับความสำคัญโดยให้เหตุผลรองรับผ่าน 4 มิติ ได้แก่ Value (คุณค่าต่อ Stakeholder), Risk (ความเสี่ยงหากไม่ทำ), Urgency (ความเร่งด่วนใน Workflow), และ Dependency (ความเกี่ยวเนื่องกับฟีเจอร์/หลักฐานอื่น)
  - **Must:** จำเป็นต้องมีต่อ Workflow หลัก หากขาดไปสุ่มเสี่ยงต่อการเกิดปัญหาข้อมูลตกหล่นในแชต (E-01) หรือไม่มีหลักฐานยืนยันงานเสร็จ (E-02)
  - **Should:** สำคัญมาก ช่วยเพิ่มความโปร่งใสและลดความขัดแย้ง (เช่น History Log และคะแนน Peer Evaluation) แต่ยังพอมี Workaround ชั่วคราวได้ในรอบแรก
  - **Could:** มีประโยชน์ ช่วยอำนวยความสะดวก แต่ไม่ด่วน สามารถเลื่อนไปพัฒนารุ่นถัดไปได้
  - **Won't (current release):** สิ่งที่อยู่นอกขอบเขต (Out of Scope) ตาม Problem Brief เช่น ระบบ Chat, Video Call, หรือการเชื่อมระบบเกรดของมหาวิทยาลัย

## 3. Non-functional Requirements

| ID | Quality Attribute | Requirement Statement | Measure / Criterion | Priority | Status |
|---|---|---|---|---|---|
| NFR-01 | Usability | ระบบต้องใช้งานง่าย ไม่ซับซ้อน เพื่อให้สมาชิกทุกคนอัปเดตงานได้โดยไม่รู้สึกเป็นภาระ | สมาชิกใหม่อัปเดตสถานะงานครั้งแรกได้สำเร็จภายใน 5 นาที โดยไม่ต้องมีการอบรม | Must | Ready |
| NFR-02 | Privacy | ข้อมูลของแต่ละกลุ่มต้องมองเห็นได้เฉพาะสมาชิกในกลุ่มและอาจารย์ที่เกี่ยวข้องเท่านั้น (แยกข้อมูลตามกลุ่ม/รายวิชา) | ทดสอบด้วยบัญชีต่างกลุ่มแล้วไม่สามารถเห็นข้อมูลของกลุ่มอื่นได้ | Must | Ready |
| NFR-03 | Reliability | ประวัติการเปลี่ยนแปลงงาน (เช่น การเปลี่ยนเจ้าของงาน) ต้องน่าเชื่อถือและไม่ถูกแก้ไข/ลบย้อนหลังโดยสมาชิกทั่วไป | ทดสอบแก้ไข/ลบประวัติด้วยบัญชีสมาชิกทั่วไปแล้วระบบปฏิเสธการทำรายการ | Should | Ready |
| NFR-04 | Usability (Psychological) | การแสดงผลประวัติงาน (History Log) ต้องใช้ภาษาที่เป็นกลาง (Neutral wording) เพื่อลดความขัดแย้งในทีม | ไม่มีคำในเชิงตำหนิหรือแสดงข้อผิดพลาดของบุคคลบน UI อย่างโจ่งแจ้ง | Should | Ready |
| NFR-05 | Accessibility | ระบบต้องใช้งานได้ทั้งบนคอมพิวเตอร์และสมาร์ตโฟน เนื่องจากสมาชิกส่วนใหญ่ใช้มือถือเป็นหลัก | เปิดหน้าหลักและอัปเดตสถานะงานได้ครบถ้วนบนหน้าจอมือถือโดยไม่ต้อง zoom | Must | Needs Follow-up |

## 4. Business Rules / Constraints

| ID | Rule / Constraint | Rationale | Related FR/NFR |
|---|---|---|---|
| BR-01 | การเปลี่ยนสถานะงานเป็น "เสร็จสิ้น (Done)" จะถูกบังคับให้ต้องแนบไฟล์หรือลิงก์หลักฐานเสมอ | เพื่อให้การพิจารณางานเสร็จสิ้นมีข้อมูลอ้างอิงที่ตรวจสอบได้ และลดข้อขัดแย้งตอนประเมิน (E-02) | FR-03, FR-04 |

| BR-04 | ทุกการเปลี่ยนเจ้าของงานต้องถูกบันทึกพร้อมเหตุผลและเวลา (timestamp) โดยไม่สามารถลบภายหลังได้ | เพื่อให้มีหลักฐานย้อนหลังสนับสนุนการประเมินอย่างเป็นธรรม (E-03) | FR-05, NFR-03 |
