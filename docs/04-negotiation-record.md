# 04 — Negotiation Record

> **Week 4 deliverable**
> บันทึกข้อขัดแย้งของความต้องการ (Conflict) ทางเลือก (Options) และข้อสรุปการตัดสินใจ

## 1. Resolved Issues (ข้อขัดแย้งที่ได้ข้อสรุปแล้ว)

| Issue ID | ประเด็นข้อขัดแย้ง (Conflict/Issue) | Stakeholders ที่เกี่ยวข้อง | ทางเลือกที่พิจารณา (Options) | ข้อสรุป / การตัดสินใจ (Resolution) | เหตุผลรองรับ (Rationale) |
|---|---|---|---|---|---|
| **IS-01** | **ระดับสิทธิ์การเข้าถึงข้อมูลของอาจารย์ผู้สอน**<br>อาจารย์ต้องการเห็นความคืบหน้าของงานเพื่อประเมินผล แต่นักศึกษาต้องการพื้นที่ปลอดภัย (Safe space) ระหว่างทำงาน ไม่อยากให้ถูกจับผิดงานที่ยังไม่เสร็จ (Work in progress) | อาจารย์ผู้สอน <br>vs<br> นักศึกษา (สมาชิกกลุ่ม) | 1. ให้อาจารย์เห็นงานและประวัติทุกอย่างเหมือนนักศึกษา<br>2. ให้อาจารย์เห็นเฉพาะตอนปิดโปรเจกต์ทีเดียว<br>3. ให้อาจารย์เห็นหน้า Dashboard ภาพรวม (สัดส่วนงาน) และไฟล์งานขั้นสุดท้ายเท่านั้น | **เลือก Option 3**<br>(จำกัดสิทธิ์อาจารย์เป็น Read-only เฉพาะ Dashboard และงานที่สถานะ Done) | เพื่อสร้างสมดุลระหว่าง "ความโปร่งใสในการประเมินผล" และ "สภาพจิตใจของนักศึกษา" ให้นักศึกษากล้าลองผิดลองถูกระหว่างทำงานได้โดยไม่กดดัน |
| **IS-02** | **ความโปร่งใส vs การบั่นทอนจิตใจ (History Log)**<br>เมื่อมีการเปลี่ยนผู้รับผิดชอบงาน หัวหน้ากลุ่มต้องการให้โชว์ประวัติว่าใครทิ้งงาน แต่สมาชิกกลุ่มกังวลว่าระบบจะกลายเป็นเครื่องมือประจาน (Blaming) และสร้างความขัดแย้ง | หัวหน้ากลุ่ม <br>vs<br> สมาชิกกลุ่ม | 1. ไม่เก็บประวัติคนเก่า ลบข้อมูลทิ้งไปเลย<br>2. เก็บประวัติและแสดงข้อความแจ้งเตือนอย่างชัดเจนว่าใครทำงานไม่เสร็จ<br>3. เก็บประวัติครบถ้วนเพื่อความโปร่งใส แต่แสดงผลบน UI ด้วยภาษาที่เป็นกลาง (Neutral wording) | **เลือก Option 3**<br>(ระบบเก็บบันทึกประวัติห้ามลบ แต่ดีไซน์ UI ต้องไม่ใช้คำในเชิงตำหนิ) | จำเป็นต้องเก็บข้อมูลเพื่อลดข้อพิพาทตอนทำ Peer Evaluation แต่ต้องรักษาบรรยากาศการทำงานกลุ่มไม่ให้แย่ลง (Psychological Usability) |
| **IS-03** | **ข้อจำกัดทางเทคนิคในการแนบหลักฐาน (Definition of Done)**<br>กฎบังคับให้ต้องแนบไฟล์งานก่อนกดเสร็จ แต่ไฟล์งานบางประเภท (เช่น วิดีโอ, ซอร์สโค้ด) มีขนาดใหญ่มาก หากบังคับให้อัปโหลดเข้าระบบโดยตรงอาจทำให้ Server เต็ม | ฝ่ายพัฒนาระบบ <br>vs<br> ผู้ใช้งาน (สมาชิก) | 1. บังคับอัปโหลดไฟล์เข้าระบบเท่านั้น พร้อมจำกัดขนาดไฟล์<br>2. อนุญาตให้ส่งเป็นลิงก์ (URL) ไปยัง External Cloud (เช่น Google Drive, GitHub) หรือข้อความอธิบายได้ | **เลือก Option 2**<br>(รองรับหลักฐานแบบ ไฟล์, ลิงก์ และ ข้อความ) | ให้ความยืดหยุ่นกับผู้ใช้ตามประเภทของงาน และช่วยลดภาระต้นทุนในการจัดเก็บข้อมูล (Storage) ของระบบ |

## 2. Unresolved / Pending Issues (ประเด็นที่ยังรอการตัดสินใจ)

| Issue ID | ประเด็นข้อขัดแย้ง (Conflict/Issue) | Stakeholders ที่เกี่ยวข้อง | ทางเลือกที่พิจารณา (Options) | สิ่งที่ต้องทำต่อ (Next Step / Validation) |
|---|---|---|---|---|
| **IS-04** | **เงื่อนไขการล็อกระบบ Peer Evaluation**<br>ระบบควรอนุญาตให้สมาชิกเข้าทำแบบประเมินเพื่อนร่วมทีมได้ตั้งแต่เมื่อไหร่? | ทีมวิเคราะห์ Requirement <br>vs<br> อาจารย์ผู้สอน | 1. เปิดให้ทำแบบประเมินได้ตลอดเวลาตั้งแต่เริ่มโปรเจกต์<br>2. ระบบจะล็อกไว้ และเปิดให้ประเมินได้เฉพาะตอนที่งานของกลุ่มถูกทำเครื่องหมายว่า "เสร็จสิ้น (Done)" แล้วเท่านั้น | ต้องนำประเด็นนี้ไปตั้งเป็น Assumption ใน Week 05 และสอบถามอาจารย์ผู้สอนเพื่อยืนยันกฎ (Business Rule) ข้อนี้อย่างเป็นทางการ |
| **IS-05** | **ระบบแจ้งเตือน (Notification)**<br>การแจ้งเตือนเตือนงานใกล้ถึงกำหนดส่ง เป็นสิ่งที่จำเป็นต้องมีในระบบตัวแรก (MVP) หรือไม่? เพราะอาจใช้ Effort สูง | ทีมพัฒนา <br>vs<br> ผู้ใช้งาน | 1. พัฒนาระบบแจ้งเตือนผ่าน Email / ระบบภายใน<br>2. ตัดออกไปก่อน แล้วให้หัวหน้ากลุ่มดู Dashboard แล้วไปตามเพื่อนในแชตเอาเอง | ปรับ Status ใน Backlog เป็น Needs Follow-up เพื่อพิจารณาความคุ้มค่า (Value vs Effort) อีกครั้ง |
