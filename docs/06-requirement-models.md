## 2. Acceptance Criteria

### AC-01: การแสดงรายการงานและกำหนดส่ง (Linked: US-01 / FR-01)
* **AC-01-01 (Happy Path):**
  * **Given** สมาชิกกลุ่มเข้าสู่ระบบสำเร็จ
  * **When** เปิดเข้ามายังหน้าหลัก (Task Board / My Tasks)
  * **Then** ระบบต้องแสดงรายการงานทั้งหมดที่ตนเองรับผิดชอบ พร้อมชื่อหัวข้องาน สถานะปัจจุบัน และวันกำหนดส่งอย่างชัดเจน โดยไม่ต้องตั้งตัวกรองค้นหาเอง
* **AC-01-02 (Empty State):**
  * **Given** สมาชิกยังไม่ได้รับมอบหมายงานใดๆ
  * **When** เปิดดูหน้ารายการงานของตนเอง
  * **Then** ระบบต้องแสดงข้อความว่า "ยังไม่มีงานที่ได้รับมอบหมายในขณะนี้"

### AC-02: การสร้างและมอบหมายงาน (Linked: US-02 / FR-02)
* **AC-02-01 (Success):**
  * **Given** ผู้ใช้เข้าสู่ระบบด้วยสิทธิ์ "หัวหน้ากลุ่ม"
  * **When** กรอกชื่องาน, เลือกผู้รับผิดชอบจากรายชื่อสมาชิกในกลุ่ม, ระบุวันกำหนดส่ง แล้วกดปุ่ม "สร้างงาน"
  * **Then** งานชิ้นใหม่ต้องบันทึกลงระบบ และไปปรากฏในรายการงานของผู้รับผิดชอบทันที
* **AC-02-02 (Validation Check):**
  * **Given** หัวหน้ากลุ่มกำลังสร้างงานใหม่
  * **When** ไม่ระบุชื่อผู้รับผิดชอบ หรือเว้นว่างวันกำหนดส่ง แล้วกดบันทึก
  * **Then** ระบบต้องปฏิเสธการบันทึก และแจ้งเตือนให้กรอกข้อมูลจำเป็นให้ครบถ้วน

### AC-03: การอัปเดตสถานะงานเรียลไทม์ (Linked: US-03 / FR-03, BR-02)
* **AC-03-01 (State Transition & Real-time):**
  * **Given** สมาชิกเปิดการ์ดงานที่ตนเองเป็นเจ้าของ
  * **When** ทำการเปลี่ยนสถานะงานจาก "To-do" เป็น "Doing"
  * **Then** สถานะงานเปลี่ยนเป็น Doing ทันที และหน้าจอของสมาชิกคนอื่นในกลุ่มเห็นการเปลี่ยนแปลงโดยไม่ต้องรีเฟรชหน้าจอเกิน 1 ครั้ง

### AC-04: การบังคับแนบหลักฐานก่อนปิดงาน (Linked: US-04 / FR-04, BR-01)
* **AC-04-01 (Validation Enforcement - Rule BR-01):**
  * **Given** สมาชิกกำลังเปิดการ์ดงานสถานะ "Doing"
  * **When** พยายามเลือกสถานะเป็น "Done" โดยยังไม่ได้อัปโหลดไฟล์ แนบ URL ลิงก์ หรือพิมพ์ข้อความหลักฐาน
  * **Then** ระบบต้องปฏิเสธการเปลี่ยนสถานะ และแสดงข้อความเตือนให้แนบหลักฐานการทำงานก่อนเสมอ
* **AC-04-02 (Success Submission):**
  * **Given** สมาชิกแนบไฟล์หรือวางลิงก์หลักฐานภายนอก (เช่น Google Drive, GitHub) ลงในช่องหลักฐานเรียบร้อยแล้ว
  * **When** กดยืนยันเปลี่ยนสถานะเป็น "Done"
  * **Then** สถานะงานเปลี่ยนเป็น Done สำเร็จ และบันทึกหลักฐานนั้นผูกติดไว้กับการ์ดงาน

### AC-05: ประวัติการเปลี่ยนผู้รับผิดชอบงาน (Linked: US-05 / FR-05, BR-04, NFR-04)[cite: 2, 13]
* **AC-05-01 (Audit Trail):**
  * **Given** หัวหน้ากลุ่มทำการเปลี่ยนผู้รับผิดชอบงานจากสมาชิก A เป็นสมาชิก B
  * **When** กดยืนยันการมอบหมายใหม่
  * **Then** ระบบต้องบันทึกประวัติ (History Log) ระบุชื่อคนเดิม, ชื่อคนใหม่, วันเวลา (Timestamp) และคงไฟล์งานเดิมไว้ครบถ้วน
* **AC-05-02 (Psychological Usability - NFR-04):**
  * **Given** สมาชิกเปิดดูแถบ Task History Log
  * **When** มีรายการเปลี่ยนตัวผู้รับผิดชอบงาน
  * **Then** ข้อความที่แสดงต้องใช้ภาษาที่เป็นกลาง (Neutral wording) เช่น "ส่งมอบงานต่อให้ [ชื่อสมาชิก]" โดยไม่มีข้อความเชิงลบหรือตำหนิบน UI

### AC-06: สิทธิ์และการแสดงผล Dashboard ของอาจารย์ (Linked: US-06 / FR-06, FR-07, BR-03, NFR-01)
* **AC-06-01 (Read-only Restriction - BR-03):**
  * **Given** อาจารย์ผู้สอนเข้าสู่ระบบและเปิดดูหน้ารายละเอียดกลุ่ม 07
  * **When** เปิดหน้า Dashboard สรุปความคืบหน้า
  * **Then** ระบบต้องแสดงสัดส่วนงานที่เสร็จ (Done) และงานคงค้างของสมาชิกแต่ละคนในรูปแบบอ่านอย่างเดียว (Read-only) โดยไม่มีปุ่มแก้ไข/ลบงาน
* **AC-06-02 (Privacy & Evidence Access - NFR-02, IS-02):**
  * **Given** อาจารย์เปิดดูรายการงานของกลุ่ม
  * **When** คลิกดูรายละเอียดงาน
  * **Then** อาจารย์สามารถคลิกเปิดดูไฟล์หลักฐานของงานสถานะ "Done" ได้ แต่ระบบต้องไม่แสดงรายละเอียดการสื่อสารภายในหรืองานระหว่างทำ (Work-in-progress)

### AC-07: การทำแบบประเมินอิงหลักฐาน (Linked: US-07 / FR-08, BR-04)
* **AC-07-01 (Evidence-backed Evaluation):**
  * **Given** สมาชิกเข้าสู่ระบบในช่วงเปิดรอบทำ Peer Evaluation เมื่อสิ้นสุดโปรเจกต์
  * **When** เปิดแบบฟอร์มประเมินเพื่อนร่วมทีม
  * **Then** ระบบต้องดึงรายการงานและลิงก์หลักฐานที่เพื่อนคนนั้นทำเสร็จ (Done) มาแสดงบนหน้าจอควบคู่กับเกณฑ์การให้คะแนน

### AC-08: การสรุปคะแนน Peer Evaluation (Linked: US-08 / FR-09)
* **AC-08-01 (Automated Calculation):**
  * **Given** สมาชิกทุกคนในกลุ่มส่งแบบประเมินครบถ้วน
  * **When** อาจารย์ผู้สอนหรือหัวหน้ากลุ่มเปิดดูรายงานผลสรุป
  * **Then** ระบบต้องคำนวณคะแนนเฉลี่ยและสรุป Feedback ข้อคิดเห็นของสมาชิกแต่ละคนออกมาให้อัตโนมัติโดยไม่ต้องรวบรวมเอง

### AC-09: การเข้าถึงสำหรับผู้บกพร่องทางการมองเห็น (Linked: US-09 / R-1, R-2)
* **AC-09-01 (Keyboard Trapping & Navigation):**
  * **Given** สมาชิกใช้งานผ่านคีย์บอร์ดโดยไม่ใช้เมาส์
  * **When** กดปุ่ม Tab, Shift+Tab, Enter และ Space
  * **Then** ผู้ใช้ต้องสามารถเลื่อน Focus ไปยังปุ่ม ฟอร์ม และสั่งเปลี่ยนสถานะงานได้ครบถ้วน โดยไม่ติดกับดักคีย์บอร์ด (No mouse trap)
* **AC-09-02 (Screen Reader Compatibility):**
  * **Given** สมาชิกเปิดโปรแกรม Screen Reader (เช่น NVDA / VoiceOver)
  * **When** Focus เลื่อนไปยังการ์ดงานและปุ่มคำสั่ง
  * **Then** โปรแกรมอ่านหน้าจอต้องอ่านชื่อป้ายกำกับ (ARIA Label) สถานะงาน และข้อความแจ้งเตือนออกมาเป็นเสียงสังเคราะห์ได้อย่างถูกต้อง

### AC-10: การทำงานออฟไลน์และซิงก์ข้อมูล (Linked: US-10 / R-3, R-4)
* **AC-10-01 (Local Cache Reading):**
  * **Given** อุปกรณ์ของสมาชิกขาดการเชื่อมต่ออินเทอร์เน็ตระหว่างใช้งาน
  * **When** เปิดดูรายการงานและกำหนดส่ง
  * **Then** ระบบต้องดึงข้อมูลล่าสุดจากแคชภายในเครื่องมาแสดงผลได้ต่อเนื่อง พร้อมแสดงแถบเตือนสถานะ Offline
* **AC-10-02 (Action Queue & Auto-sync):**
  * **Given** ผู้ใช้กดเปลี่ยนสถานะงานในขณะที่ระบบอยู่ในสถานะ Offline
  * **When** สัญญาณอินเทอร์เน็ตกลับมาเชื่อมต่อสำเร็จ
  * **Then** คำสั่งที่ค้างอยู่ในคิวภายในเครื่องต้องถูกส่งขึ้นเซิร์ฟเวอร์ และอัปเดตสถานะงานให้อัตโนมัติโดยข้อมูลไม่สูญหาย

## 6. Negotiation / Trade-off Notes

บันทึกสิ่งที่ไม่ได้เลือกหรือเลื่อนออกจาก scope พร้อมเหตุผล[cite: 16]

| ประเด็น / ID | ทางเลือกที่พิจารณา (Options) | ข้อสรุปการตัดสินใจ (Decision) | ข้อแลกเปลี่ยน / ผลกระทบ (Trade-offs) | สถานะ / Traceability |
| :---| :---| :---| :---| :---: |
| **การแสดงประวัติการเปลี่ยนเจ้าของงาน**<br>(History Log / IS-01) | **A:** ซ่อนประวัติเก่าทั้งหมดเพื่อรักษาสภาพจิตใจสมาชิกที่ทำไม่ไหว<br>**B:** แสดงประวัติทั้งหมดเพื่อความโปร่งใสและเพื่อให้นำงานไปทำต่อได้ | **เลือก B แต่ปรับการแสดงผล:** แสดงประวัติทั้งหมดเพื่อให้ผู้รับช่วงต่อทำงานได้ทันที แต่บังคับใช้ภาษาที่เป็นกลาง (Neutral wording) | **Trade-off:** เพิ่มความโปร่งใสและประสิทธิภาพการส่งต่องาน โดยควบคุม Usability ไม่ให้เกิดความรู้สึกลบในทีม | **Resolved**<br>(`docs/05`: FR-05, NFR-04, US-05) |
| **สิทธิ์การเข้าถึงของอาจารย์ผู้สอน**<br>(Instructor View / IS-02) | **A:** อาจารย์ดูรายละเอียดได้ทุกจุด ทุกสถานะ และอ่านแชตได้<br>**B:** อาจารย์ดูได้เฉพาะภาพรวม Dashboard และหลักฐานงานที่ส่งแล้ว (Done) | **เลือก B (จำกัดสิทธิ์ Read-only):** ให้เห็นเฉพาะข้อมูลเชิงประจักษ์ขั้นสุดท้ายและ Worklog ที่ส่งแล้วเท่านั้น | **Trade-off:** อาจารย์ไม่ได้เห็นการแก้ปัญหาระหว่างทางยิบย่อย แต่นักศึกษาได้ Safe Space ในการทำงานร่วมกัน | **Resolved**<br>(`docs/05`: FR-06, FR-07, BR-03, US-06) |
| **ระบบแจ้งเตือนกำหนดส่งงาน**<br>(FR-10) | **A:** พัฒนาระบบ Push Notification และ LINE Bot แจ้งเตือน<br>**B:** เลื่อนไปทำเวอร์ชันถัดไป (Deferred) เนื่องจากขาดหลักฐานสนับสนุน | **เลือก B (Deferred):** สมาชิกยังสามารถดูวันกำหนดส่งได้ชัดเจนจากหน้า Task Board ส่วนตัว (FR-01) | **Trade-off:** ลดภาระการพัฒนาและการผูก API ภายนอก โดยให้สมาชิกติดตามกำหนดส่งผ่านหน้าจอหลักแทน | **Deferred**<br>(Priority Could / Needs Follow-up) |
| **การบันทึกข้อตกลงการทำงานกลุ่ม**<br>(Team Agreement / FR-12) | **A:** สร้างระบบบันทึกและเซ็นรับรองข้อตกลงแบบ Interactive ภายในระบบ<br>**B:** ใช้ข้อตกลงนอกระบบ และเลื่อนฟังก์ชันนี้ออกไปก่อน | **เลือก B (Deferred):** กำหนดให้ทีมตกลงเกณฑ์กันเบื้องต้น และให้ระบบโฟกัสที่การทำ Peer Evaluation ตอนปิดโปรเจกต์ก่อน | **Trade-off:** ประหยัดเวลาการออกแบบ Data Model แต่ต้องอาศัยการสื่อสารกันเองของสมาชิกในช่วงเริ่มต้นโครงการ | **Deferred**<br>(Priority Could / A-03) |
| **ระบบแชตและวิดีโอคอลในตัวระบบ**<br>(In-app Chat / Video Call) | **A:** เพิ่มห้องแชตและโทรในระบบติดตามงาน<br>**B:** ตัดออกจากขอบเขต (Out of Scope / Won't) | **เลือก B (Won't):** ให้นักศึกษาใช้แอปพลิเคชันเดิมที่ถนัด (LINE / Discord) และให้ระบบโฟกัสเฉพาะการ Track งานและเก็บหลักฐาน | **Trade-off:** ผู้ใช้ต้องสลับแอปเพื่อคุยงาน แต่ระบบไม่บวม และแก้ปัญหาข้อมูลงานหายในแชตได้อย่างตรงจุด | **Won't (Current Release)**<br>(`docs/01`, `docs/05` Scope) |
